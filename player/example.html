Integration component

APK Player

A <apk-player> element (and the ApkPlayer class) that runs a real Android APK inside your page, in the visitor's browser, with the same VM and the same features as the lab's test page.

The APK runs in an iframe served by the runtime origin, which shows only the emulated device (screen, status bar, navigation bar). The Dalvik VM runs in a Web Worker of that frame. Your page talks to it through versioned postMessage, validated on both sides. Everything the test page offers in the Controls panel (virtual device, network, host redirects, endpoint mocks, permissions, method returns, ignored Activities, time per event, memory, Intents, app data, Logcat, network, Compose, layout bounds, diagnostics and plugins) is available through options and methods, over the same Worker paths.

Embed

    
Publish the lab's dist/ folder (the node scripts/build-web.mjs build) as a static site, preferably on an origin used only for the runtime (for example https://apk-runtime.your-site.com). In your page:

    
<script type="module" src="https://YOUR-RUNTIME/player/apk-player.js"></script>

<apk-player src="/apks/app-debug.apk"
            device="phone" locale="pt-BR" theme="dark" orientation="portrait"
            allowed-hosts="api.example.com"
            style="height:720px"></apk-player>

    
    
      
  • Size. The element is a block that takes the available width; the default height is 640 px (set it with CSS). The device is scaled to fit the space (scale="actual" keeps 1 CSS px per dp, for pixel comparison).
    • 
      
  • Origins. assetsBase (attribute assets-base) is the folder that player/frame.html, the Worker, the framework and the WASM come from; the default is the folder above apk-player.js. The frame receives your page's origin in ?parent= and only accepts messages from it.
    • 
      
  • Who can embed it. Any page can frame frame.html by declaring its own origin. Restrict it on the runtime host with Content-Security-Policy: frame-ancestors https://your-site.com.
    • 
      
  • Lazy loading. loading="lazy" (or lazy: true) only creates the frame when it becomes visible. Each player has its own Worker and its own memory: keep few of them at the same time.
    • 
      
  • Opaque host page. file:// pages or sandboxed pages without allow-same-origin are refused (error with kind: "opaque-host-origin"): serve over http(s).
    • 
    

    
With the class

    
import { ApkPlayer } from 'https://YOUR-RUNTIME/player/apk-player.js';

const player = ApkPlayer.mount(document.querySelector('#slot'), {
  apk: file,                                 // File | Blob | ArrayBuffer | URL
  config: { device: 'tablet', theme: 'dark', allowedHosts: ['*'] },
  plugins: [],                                  // optional: plugins from the start
});
player.addEventListener('ready', e => console.log('running', e.detail.activity));
// …
player.destroy();

Network: allowed hosts and relay

    
The player's default is to reach no host at all (the name fails as on a device without a connection). The request goes out through the browser's fetch (CORS applies) or through the relay you operate.

    
await player.configure({ network: { allowedHosts: ['api.example.com', '*.cdn.example.com'], proxyUrl: 'https://relay.your-site.com/?u={url}' } });


    
Redirect hosts

    
The app asks for the original URL; the exchange goes to another destination (for example your local development server). The app keeps seeing the URL it asked for.

    
await player.configure({ hostMap: [{ from: 'api.example.com', to: 'localhost:8080' }], allowedHosts: ['localhost:8080'] });
// attribute: host-map="api.example.com -> localhost:8080"

CORS: when the app's network fails in the browser

    
On the virtual device, every HTTP request of the app (HttpURLConnection, OkHttp and anything else on top of java.net) becomes a browser fetch, made by the VM Worker on the runtime origin (that of player/frame.html, not your page's). The browser only hands over a response from another site if that server authorizes this origin with CORS. The servers an app talks to almost never authorize it, because they were built for apps, not for pages.

    
    
      
  • Response without CORS. Without Access-Control-Allow-Origin carrying the runtime origin (or *), the browser discards the response.
    • 
      
  • Preflight. “Non-simple” requests (methods other than GET/HEAD/POST, headers such as Authorization or Content-Type: application/json) first send an OPTIONS; if the server does not answer it with the right headers, the request is never sent.
    • 
      
  • Response headers. Besides the basic ones, the app only sees the headers the server lists in Access-Control-Expose-Headers.
    • 
      
  • Cookies and credentials. The lab makes every fetch with credentials: "omit": browser cookies never go along, and the app's Cookie, User-Agent and Set-Cookie do not pass through the browser (only through a relay). That is why Access-Control-Allow-Credentials is not needed.
    • 
      
  • Local network from an https page. A destination on localhost or on the local network, requested by a public origin, goes through the browser's private network access rules: depending on the browser and version, it requires the Access-Control-Allow-Private-Network: true response in the preflight or asks the visitor for local network access permission. (http://localhost does not count as mixed content; other http:// destinations from an https page are blocked.)
    • 
    

    
How the failure shows up

    
The browser does not tell the page why a fetch failed: CORS refused, unreachable host and extension blocking give the same error. So the app receives what a device with no route would receive, java.net.ConnectException: failed to connect to host/host (port 443): the browser reports unreachable hosts, CORS rejections and blocked requests identically (…). In the network log (the lab's Network panel, or player.network.subscribe) the entry has outcome: "error" and that message in failure.message; the panel adds the hint that only the browser console says what the cause was. The console shows “blocked by CORS policy” when it was CORS.

    
1. Local CORS relay

    
A small program that runs on your computer and repeats each request from there, as the device would, answering the page with CORS. Download cors-relay.mjs (published on the site at tools/cors-relay.mjs; Node 18 or newer) and run:

    
node cors-relay.mjs
# APK Web Lab CORS relay on http://127.0.0.1:8787 (only this machine can reach it)
# Allowed page origins: https://madmax-dev-br.github.io, http://127.0.0.1:8765, http://localhost:8765
# Proxy field (Controls > Device): http://127.0.0.1:8787/<token>/?url={url}

    
Paste the printed “Proxy” URL into the player's proxyUrl (or into Controls › Device › Proxy on the lab page). {url} is where the lab puts the destination (encoded with encodeURIComponent; without {url}, the destination is appended at the end). The hosts are still decided by allowedHosts.

    
<apk-player src="app.apk" allowed-hosts="*" proxy-url="http://127.0.0.1:8787/YOUR-TOKEN/?url={url}"></apk-player>
<!-- or -->
await player.configure({ network: { allowedHosts: ['*'], proxyUrl: 'http://127.0.0.1:8787/YOUR-TOKEN/?url={url}' } });

    

      
OptionEffect

      
        
--port 8787Port (on 127.0.0.1 only: no other machine reaches the relay).

        
--origin <origin>Accepted page origin (repeatable). The default is the public site and a local copy on port 8765. In the player, the origin that counts is the runtime's (where player/frame.html is): if you host the runtime, pass --origin https://your-runtime.example.com.

        
--token <token>Secret in the URL path (by default, a random one at each start): another site open in the same browser cannot use the relay.

      

    
The relay reaches any destination the page asks for, including servers on this computer or on the local network. It follows redirects, returns Set-Cookie (which the browser hides) as x-apkweb-set-cookie, sends the app's Cookie/User-Agent, answers the preflight (including with Access-Control-Allow-Private-Network) and turns “unknown host”, “refused”, “timed out” and certificate errors into the exception Android would throw. It stores nothing. It does not solve blocking by browser extensions, nor services the virtual device does not have.

    
2. Endpoint mocks

    
Fixed responses served inside the lab: the request never reaches the network, so there is no CORS. Good for screens that only need plausible data.

    
await player.configure({ endpointMocks: [{ method: 'GET', url: 'https://api.example.com/v1/*', status: 200,
  headers: [{ name: 'Content-Type', value: 'application/json' }], body: '{"items":[]}' }] });

    
3. Redirect to a server of your own that answers CORS

    
Point the app's host at a server you control (for example the development backend) and make that server authorize the runtime origin. The app keeps seeing the original URL. (With a relay on, the relay repeats the already redirected destination.)

    
await player.configure({ hostMap: [{ from: 'api.example.com', to: 'localhost:8080' }], allowedHosts: ['api.example.com', 'localhost:8080'] });

    
The backend must answer CORS for the runtime origin, including the preflight, and allow local network access. Integrate with your backend has a complete Node server and a complete Micronaut one.

    
Access-Control-Allow-Credentials is not needed: the lab never sends browser credentials.

    
4. Run the VM on the server

    
Outside the browser there is no CORS: the Node services in the public apk-lab-node-service repository run the same VM in Node, and there the app's requests go out directly from the server, with cookies, User-Agent and redirects as on a device. It is the path for automation or for apps whose servers cannot be reached from a page.


    
Integrate with your backend (Node and Micronaut)

    
When the app talks to an API you develop, the most direct path is to point it at the backend running on your computer and make that backend accept the player's runtime. There are three parts: the redirect in the player, CORS on the backend and the local network permission. The two examples below do all three and expose the same small API: GET /v1/hello and POST /v1/echo.

    
In the player: redirect the API host

    
The app keeps using the production URL; only the network exchange goes to your server. A localhost destination without a scheme becomes http://, so the local backend needs no TLS. The app sees the connection as HTTPS with the lab's certificate, which works with OkHttp and HttpURLConnection; an app that pins the real server's certificate refuses this connection, as it would behind a proxy.

    
await player.configure({
  hostMap: [{ from: 'api.example.com', to: 'localhost:8080' }],   // the app keeps asking for https://api.example.com
});
// an app built for the emulator, which calls http://10.0.2.2:8080:
await player.configure({ hostMap: [{ from: '10.0.2.2', to: 'localhost' }] });
// or on the element: <apk-player src="app.apk" host-map="api.example.com -> localhost:8080"></apk-player>

    
The origin the backend must accept is the runtime's, that of player/frame.html, and not your page's: https://madmax-dev-br.github.io for the published player, or the origin you serve a copy of it from.

    
Node

    
No dependencies (Node 18 or newer). Save it as server.mjs and run node server.mjs; ORIGINS accepts several origins separated by commas, and PORT changes the port.

    
// Development backend for an app running in the APK Player: CORS for the runtime origin, preflight and local network access.
import http from 'node:http';
import { randomUUID } from 'node:crypto';

const PORT = Number(process.env.PORT ?? 8080);
const ORIGINS = (process.env.ORIGINS ?? 'https://madmax-dev-br.github.io').split(',');   // the origin of player/frame.html

function cors(req, res) {
  const origin = req.headers.origin;
  if (!ORIGINS.includes(origin)) return;
  res.setHeader('Access-Control-Allow-Origin', origin);
  res.setHeader('Vary', 'Origin');
  res.setHeader('Access-Control-Expose-Headers', 'X-Request-Id');   // the response headers the app reads
  if (req.method === 'OPTIONS') {                                   // preflight: Authorization, Content-Type: application/json, PUT, DELETE...
    res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, PATCH, DELETE');
    res.setHeader('Access-Control-Allow-Headers', req.headers['access-control-request-headers'] ?? '');
    if (req.headers['access-control-request-private-network']) res.setHeader('Access-Control-Allow-Private-Network', 'true');
    res.setHeader('Access-Control-Max-Age', '600');
  }
}

const json = (res, status, value) => { res.writeHead(status, { 'Content-Type': 'application/json', 'X-Request-Id': randomUUID() }); res.end(JSON.stringify(value)); };

http.createServer(async (req, res) => {
  cors(req, res);
  if (req.method === 'OPTIONS') { res.writeHead(204); return res.end(); }
  const { pathname } = new URL(req.url, 'http://localhost');
  if (req.method === 'GET' && pathname === '/v1/hello') return json(res, 200, { message: 'Hello from Node' });
  if (req.method === 'POST' && pathname === '/v1/echo') {
    let body = ''; for await (const part of req) body += part;
    return json(res, 200, JSON.parse(body || '{}'));
  }
  json(res, 404, { error: `${req.method} ${pathname} does not exist` });
}).listen(PORT, '127.0.0.1', () => console.log(`http://127.0.0.1:${PORT} (origins: ${ORIGINS.join(', ')})`));

    
Micronaut

    
Tested with Micronaut 4.10 and Java 21, in a project from Micronaut Launch (Java, Gradle). Micronaut's own CORS filter answers the preflight; allow-private-network (since 4.3) adds the local network header. The controller:

    
package example;

import io.micronaut.http.HttpResponse;
import io.micronaut.http.MediaType;
import io.micronaut.http.annotation.Body;
import io.micronaut.http.annotation.Controller;
import io.micronaut.http.annotation.Get;
import io.micronaut.http.annotation.Post;
import io.micronaut.serde.annotation.Serdeable;
import java.util.UUID;

@Controller("/v1")
public class ExampleController {

    @Serdeable
    public record Message(String message) {}

    @Get("/hello")
    public HttpResponse<Message> hello() {
        return HttpResponse.ok(new Message("Hello from Micronaut"))
                .header("X-Request-Id", UUID.randomUUID().toString());
    }

    @Post(value = "/echo", consumes = MediaType.APPLICATION_JSON, produces = MediaType.APPLICATION_JSON)
    public String echo(@Body String body) {
        return body;
    }
}

    
And in src/main/resources/application.properties:

    
micronaut.server.port=8080
micronaut.server.cors.enabled=true
# the runtime origin (player/frame.html); add that of a local copy of the lab, if you use one
micronaut.server.cors.configurations.lab.allowed-origins[0]=https://madmax-dev-br.github.io
micronaut.server.cors.configurations.lab.exposed-headers[0]=X-Request-Id
micronaut.server.cors.configurations.lab.allow-private-network=true
micronaut.server.cors.configurations.lab.max-age=600

    
Run with ./gradlew run. Micronaut only answers the preflight of routes that exist: a request with a custom header (which asks for a preflight) to a path without a route gets 403 on the OPTIONS, and the app sees ConnectException instead of a 404.

    
Check

    
Before opening the app, check the preflight the browser will send:

    
curl -si -X OPTIONS http://localhost:8080/v1/echo \
  -H 'Origin: https://madmax-dev-br.github.io' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type' \
  -H 'Access-Control-Request-Private-Network: true'
# expect 200 or 204 with Access-Control-Allow-Origin: https://madmax-dev-br.github.io,
# Access-Control-Allow-Headers with content-type and Access-Control-Allow-Private-Network: true

    
With the app running, the network log (the Network panel, or player.network.subscribe) shows each request with the original URL and the destination in mappedUrl, and the diagnostics Summary counts the responses of each rule. If the app receives java.net.ConnectException, the browser console tells the cause: “blocked by CORS policy” is the origin or a header missing in the preflight; a local network block is the missing Access-Control-Allow-Private-Network or the local network permission denied in the browser.


    
Plugins in the player

    
The lab's plugins (docs/PLUGINS.md) also run in the player, with the same lab API: lab.on('screen' | 'log' | 'network'), lab.screen(), lab.composeTree(), lab.viewModels(), lab.layoutBounds(), lab.screenshot() and lab.ui.text/kv/table/json/image/badge/clear. Each plugin runs in its own Web Worker, created on an opaque origin (a sandboxed iframe inside the frame): the code your page sends does not gain the runtime origin (nor the stored data of other apps). The output reaches your page in the plugin-output event, for you to show however you like (use textContent; images arrive as Blob).

    
const code = `
lab.on('screen', async () => {
  const boxes = (await lab.layoutBounds()).filter(c => c.kind === 'compose' && c.hasImage);
  lab.ui.badge(String(boxes.length));
  lab.ui.table(boxes.slice(0, 20).map(c => ({ name: c.name, width: c.size?.width, height: c.size?.height })), ['name', 'width', 'height'], { id: 'list' });
  if (boxes[0]) lab.ui.image(await lab.screenshot({ key: boxes[0].key, maxWidth: 360 }), { id: 'first', caption: boxes[0].name });
  lab.ui.image(await lab.screenshot({ maxWidth: 360 }), { id: 'screen', caption: 'Whole screen' });
});`;

const { plugins, rejected } = await player.plugins.set([{ id: 'components', name: 'Screen components', code: code }]);
player.plugins.subscribe(plugin => {
  for (const block of plugin.blocks) {
    if (block.kind === 'image') image.src = URL.createObjectURL(block.blob);   // revoke the previous URL
    if (block.kind === 'table') console.table(block.rows);
  }
});
await player.plugins.stop('components');

    
Limits (the same as the lab's): up to 32 plugins, 200,000 characters of code each, 16 pending queries, one composeTree per second and one image every 500 ms per plugin, images up to 8 MiB, 50 output blocks. packageFilter restricts a plugin to packages (com.example.*). Plugins that listen to log turn the Logcat stream on while they run.


    
Security and privacy

    
    
      
  • The APK stays in the browser. There is no upload: the bytes go from your page to the frame and to the Worker. The lab sends nothing of the app to any server.
    • 
      
  • Network only through the browser. The app only reaches the allowed hosts, through fetch (with the browser's CORS rules) or through the optional relay you operate. The lab neither has nor hosts a relay.
    • 
      
  • Isolation. The iframe is sandbox="allow-scripts allow-same-origin" with no permissions (allow=""). Serve the runtime on an origin different from your page's: that way the app has no access to its cookies, storage or DOM. With the same origin, the sandbox does not isolate.
    • 
      
  • Messages. Your page only accepts messages from the iframe itself and from the runtime origin; the frame only accepts the parent window, from the origin declared in ?parent=, and answers only to it. Every message is versioned and validated (bounded sizes, the same validators as the test page: sanitizeHostMap, validateMock, permissions, Intent).
    • 
      
  • Plugins on an opaque origin. The plugin code sent by your page runs in an opaque-origin Worker, with no access to the runtime's IndexedDB.
    • 
      
  • Nothing is faked. Protected native code is neither replaced nor bypassed; an API the VM does not implement fails with an explicit error (tolerant mode, which you turn on, is always reported in the diagnostics and in diagnostics()). Overrides, mocks and ignored Activities are debugging tools for your app and show up marked in the diagnostics.
    • 
      
  • Data. Only with keep-data is the app's data kept in the IndexedDB of the runtime origin, per package and certificate. The player's permission states are not stored: the permission-config event hands you the state to store, if you want.
    • 
      
  • Runtime CSP. script-src 'self' 'wasm-unsafe-eval', worker-src 'self' blob:, img-src 'self' blob: data:, connect-src 'self' plus the hosts of the APKs and of the app, frame-ancestors with your sites (and frame-src 'self' about: if you use plugins). Do not send X-Frame-Options: DENY.
    • 
    


    
Limitations

    
    
      
  • It runs what the VM supports; the rest ends with an error that states the exact frontier (frontier.kind). Native libraries, Services in other processes and many system integrations are not available.
    • 
      
  • The network is the browser's: CORS, cookies and forbidden headers, redirects followed by the browser, TLS without access to the certificates, no raw TCP/TLS sockets.
    • 
      
  • Fixed device frame (no skins), dp presets at density 160, no camera cutout.
    • 
      
  • theme changes the app's night mode, not your page's.
    • 
      
  • memoryMiB, tolerateMissing, strictCrash and webview take effect on the next start.
    • 
      
  • Images (screenshot) are cropped from the rasters already drawn: Views drawn by the page's DOM do not appear in the whole-screen image (the result says how many in notes).
    • 
      
  • Each player is a Worker with its own memory (tens to hundreds of MB depending on the APK).
    • 
    


    
Protocol

    
Messages { protocol: "apk-player", version: 1, type, … }, validated on both sides (src/player/protocol.js). Version 1 is still accepted; revision 2 is announced by the frame in hello ({ revision: 2, capabilities: [...] }) and adds, without changing the old messages:

    
    
      
  • page → frame: config with an optional id (answered in config-applied with the same id) and the keys of the lab features; call { id, method, args } with method in openIntent, inspectCompose, layoutBounds, screenshot, screenState, diagnostic, status, answerPermission, subscribe, pluginsSet, pluginsStop, pluginsRestart, pluginsList, stop.
    • 
      
  • frame → page: reply { id, ok, value | error { code, message } }, screen, logcat, network, plugin-output, permission-request, permission-config, stopped.
    • 
    

    
An old frame (revision 1) answers hello without capabilities: the new methods reject with code: "unsupported" and the rest works as before. The Markdown reference is in docs/PLAYER.md.
