Componente de integração

APK Player

Um elemento <apk-player> (e a classe ApkPlayer) que roda um APK Android de verdade dentro da sua página, no navegador do visitante, com a mesma VM e os mesmos recursos da página de testes do laboratório.

O APK roda num iframe servido pela origem do runtime, que mostra só o aparelho emulado (tela, barra de status, barra de navegação). A VM Dalvik roda num Web Worker desse frame. Sua página conversa com ele por postMessage versionado e validado dos dois lados. Tudo o que a página de testes oferece no painel Controles (dispositivo virtual, rede, redirecionamento de hosts, mocks de endpoints, permissões, retornos de métodos, Activities ignoradas, tempo por evento, memória, Intents, dados do app, Logcat, rede, Compose, limites de layout, diagnóstico e plugins) está disponível por opções e métodos, pelos mesmos caminhos do Worker.

Demonstração ao vivo

Escolha um APK seu (ele é lido pelo navegador e não sai deste computador). Quando a página roda localmente com os exemplos do laboratório, eles também aparecem na lista.

Incorporar

    
Publique a pasta dist/ do laboratório (o build node scripts/build-web.mjs) como site estático, de preferência numa origem só para o runtime (por exemplo https://apk-runtime.seu-site.com). Na sua página:

    
<script type="module" src="https://SEU-RUNTIME/player/apk-player.js"></script>

<apk-player src="/apks/app-debug.apk"
            device="phone" locale="pt-BR" theme="dark" orientation="portrait"
            allowed-hosts="api.exemplo.com"
            style="height:720px"></apk-player>

    
    
      
  • Tamanho. O elemento é um bloco que ocupa a largura disponível; a altura padrão é 640 px (defina com CSS). O aparelho é escalado para caber no espaço (scale="actual" mantém 1 px CSS por dp, para comparação de pixels).
    • 
      
  • Origens. assetsBase (atributo assets-base) é a pasta de onde vêm player/frame.html, o Worker, o framework e o WASM; o padrão é a pasta acima de apk-player.js. O frame recebe a origem da sua página em ?parent= e só aceita mensagens dela.
    • 
      
  • Quem pode incorporar. Uma página qualquer pode emoldurar frame.html declarando a própria origem. Restrinja no host do runtime com Content-Security-Policy: frame-ancestors https://seu-site.com.
    • 
      
  • Carregamento preguiçoso. loading="lazy" (ou lazy: true) só cria o frame quando ele fica visível. Cada player tem o próprio Worker e a própria memória: mantenha poucos ao mesmo tempo.
    • 
      
  • Página de origem opaca. Páginas file:// ou em sandbox sem allow-same-origin são recusadas (error com kind: "opaque-host-origin"): sirva por http(s).
    • 
    

    
Pela classe

    
import { ApkPlayer } from 'https://SEU-RUNTIME/player/apk-player.js';

const player = ApkPlayer.mount(document.querySelector('#slot'), {
  apk: arquivo,                                 // File | Blob | ArrayBuffer | URL
  config: { device: 'tablet', theme: 'dark', allowedHosts: ['*'] },
  plugins: [],                                  // opcional: plugins desde o início
});
player.addEventListener('ready', e => console.log('rodando', e.detail.activity));
// …
player.destroy();

Valores inválidos nunca são adivinhados: aparecem em rejected. ao vivo vale na hora, com a semântica do Android; próximo início vale no próximo restart() (o player avisa em rejected).

Métodos

    
Valem no elemento e na instância de ApkPlayer. Os que devolvem Promise rejeitam com um Error que tem code (bad-args, no-apk, not-found, unsupported, timeout, destroyed, vm).

    

      
setConfig(patch)

      
Mescla a configuração; o resultado chega no evento config-applied.

      
Devolve
O player

    

    

      
configure(patch)

      
O mesmo, esperando a resposta deste patch.

      
Devolve
Promise<{ config, rejected, live, outcome, statuses }>

    

    

      
reloadActivity({ mode })

      
“Recriar” (mode: 'recreate', padrão: como Activity.recreate(), estado e ViewModels mantidos) ou “Reabrir” ('reopen': nova instância com o mesmo Intent, conteúdo carregado de novo).

      
Devolve

openIntent({ data, action, component, type, category, extras })

Rede: hosts permitidos e relay

    
O padrão do player é não alcançar host nenhum (o nome falha como num aparelho sem conexão). A requisição sai pelo fetch do navegador (CORS vale) ou pelo relay que você opera.

    
await player.configure({ network: { allowedHosts: ['api.exemplo.com', '*.cdn.exemplo.com'], proxyUrl: 'https://relay.seu-site.com/?u={url}' } });


    
Redirecionar hosts

    
O app pede a URL original; a troca vai para outro destino (por exemplo seu servidor local de desenvolvimento). O app continua vendo a URL que pediu.

    
await player.configure({ hostMap: [{ from: 'api.exemplo.com', to: 'localhost:8080' }], allowedHosts: ['localhost:8080'] });
// atributo: host-map="api.exemplo.com -> localhost:8080"

Retornos de métodos e Activities ignoradas

    
Ferramentas de depuração do seu próprio app: o método substituído não executa o código original, e a abertura de uma Activity ignorada não acontece. O diagnóstico marca as duas como ativas. Métodos nativos não são substituídos.

    
await player.configure({
  methodOverrides: [{ method: 'com.exemplo.Flags.novaTela()', value: 'true' }],
  ignoredActivities: ['com.exemplo.SplashActivity'],
});

CORS: quando a rede do app falha no navegador

    
No aparelho virtual, cada requisição HTTP do app (HttpURLConnection, OkHttp e o que mais estiver por cima de java.net) vira um fetch do navegador, feito pelo Worker da VM na origem do runtime (a de player/frame.html, não a da sua página). O navegador só entrega a resposta de outro site se esse servidor autorizar essa origem com CORS. Os servidores com que um app fala quase nunca autorizam, porque foram feitos para apps, não para páginas.

    
    
      
  • Resposta sem CORS. Sem Access-Control-Allow-Origin com a origem do runtime (ou *), o navegador descarta a resposta.
    • 
      
  • Preflight. Requisições “não simples” (métodos além de GET/HEAD/POST, cabeçalhos como Authorization ou Content-Type: application/json) primeiro mandam um OPTIONS; se o servidor não responder a ele com os cabeçalhos certos, a requisição nem sai.
    • 
      
  • Cabeçalhos da resposta. Além dos básicos, o app só vê os cabeçalhos que o servidor lista em Access-Control-Expose-Headers.
    • 
      
  • Cookies e credenciais. O lab faz todo fetch com credentials: "omit": cookies do navegador nunca vão junto, e Cookie, User-Agent e Set-Cookie do app não passam pelo navegador (só por um relay). Por isso Access-Control-Allow-Credentials não é necessário.
    • 
      
  • Rede local a partir de uma página https. Um destino em localhost ou na rede local, pedido por uma origem pública, passa pelas regras de acesso à rede privada do navegador: conforme o navegador e a versão, ele exige no preflight a resposta Access-Control-Allow-Private-Network: true ou pede a permissão de acesso à rede local ao visitante. (http://localhost não conta como conteúdo misto; outros destinos http:// a partir de uma página https são bloqueados.)
    • 
    

    
Como a falha aparece

    
O navegador não diz à página por que um fetch falhou: CORS recusado, host inacessível e bloqueio por extensão dão o mesmo erro. Por isso o app recebe o que um aparelho sem rota receberia, java.net.ConnectException: failed to connect to host/host (port 443): the browser reports unreachable hosts, CORS rejections and blocked requests identically (…). No log de rede (painel Rede do laboratório, ou player.network.subscribe) a entrada fica com outcome: "error" e essa mensagem em failure.message; o painel acrescenta a dica de que só o console do navegador diz qual foi a causa. O console mostra “blocked by CORS policy” quando foi CORS.

    
1. Relay CORS local

    
Um programa pequeno que roda no seu computador e repete cada requisição a partir dali, como o aparelho faria, respondendo à página com CORS. Baixe cors-relay.mjs (publicado no site em tools/cors-relay.mjs; Node 18 ou mais novo) e rode:

    
node cors-relay.mjs
# APK Web Lab CORS relay on http://127.0.0.1:8787 (only this machine can reach it)
# Allowed page origins: https://madmax-dev-br.github.io, http://127.0.0.1:8765, http://localhost:8765
# Proxy field (Controles > Dispositivo): http://127.0.0.1:8787/<token>/?url={url}

    
Cole a URL “Proxy” impressa em proxyUrl do player (ou em Controles › Dispositivo › Proxy na página do laboratório). {url} é onde o lab põe o destino (codificado com encodeURIComponent; sem {url}, o destino é acrescentado ao fim). Os hosts continuam decididos por allowedHosts.

    
<apk-player src="app.apk" allowed-hosts="*" proxy-url="http://127.0.0.1:8787/SEU-TOKEN/?url={url}"></apk-player>
<!-- ou -->
await player.configure({ network: { allowedHosts: ['*'], proxyUrl: 'http://127.0.0.1:8787/SEU-TOKEN/?url={url}' } });

    

      
OpçãoEfeito

      
        
--port 8787Porta (só em 127.0.0.1: nenhuma outra máquina alcança o relay).

        
--origin <origem>Origem de página aceita (repetível). O padrão é o site público e uma cópia local na porta 8765. No player, a origem que conta é a do runtime (onde está player/frame.html): se você hospeda o runtime, passe --origin https://seu-runtime.exemplo.com.

        
--token <token>Segredo no caminho da URL (por padrão, um aleatório a cada início): outro site aberto no mesmo navegador não consegue usar o relay.

        
--allow-privatePermite destinos neste computador ou na rede local (loopback, faixas privadas, link-local). Sem ela o relay recusa, e o app recebe ConnectException … the CORS relay refused the target.

      

    
O relay segue redirecionamentos, devolve Set-Cookie (que o navegador esconde) como x-apkweb-set-cookie, envia Cookie/User-Agent do app, responde ao preflight (inclusive com Access-Control-Allow-Private-Network) e transforma “host desconhecido”, “recusado”, “tempo esgotado” e erro de certificado na exceção que o Android lançaria. Não guarda nada. Não resolve bloqueios de extensões do navegador nem serviços que o aparelho virtual não tem.

    
2. Mock de endpoints

    
Respostas fixas servidas dentro do laboratório: a requisição nunca chega à rede, então não existe CORS. Bom para telas que só precisam de dados plausíveis.

    
await player.configure({ endpointMocks: [{ method: 'GET', url: 'https://api.exemplo.com/v1/*', status: 200,
  headers: [{ name: 'Content-Type', value: 'application/json' }], body: '{"itens":[]}' }] });

    
3. Redirecionar para um servidor seu que responda CORS

    
Aponte o host do app para um servidor que você controla (por exemplo o backend de desenvolvimento) e faça esse servidor autorizar a origem do runtime. O app continua vendo a URL original. (Com relay ligado, o relay repete o destino já redirecionado.)

    
await player.configure({ hostMap: [{ from: 'api.exemplo.com', to: 'localhost:8080' }], allowedHosts: ['api.exemplo.com', 'localhost:8080'] });

    
Cabeçalhos que o servidor precisa enviar (troque a origem pela do seu runtime):

    
// Node (http): CORS para a origem do runtime, preflight respondido
const ORIGEM = 'https://madmax-dev-br.github.io';
http.createServer((req, res) => {
  if (req.headers.origin === ORIGEM) {
    res.setHeader('Access-Control-Allow-Origin', ORIGEM);
    res.setHeader('Vary', 'Origin');
    res.setHeader('Access-Control-Expose-Headers', 'ETag, Location, X-Request-Id');   // os que o app lê
  }
  if (req.method === 'OPTIONS') {                                     // preflight
    res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, PATCH, DELETE');
    res.setHeader('Access-Control-Allow-Headers', req.headers['access-control-request-headers'] ?? '');
    if (req.headers['access-control-request-private-network']) res.setHeader('Access-Control-Allow-Private-Network', 'true');
    res.setHeader('Access-Control-Max-Age', '600');
    res.writeHead(204); return res.end();
  }
  // … a resposta normal
}).listen(8080);

    
Access-Control-Allow-Credentials não é preciso: o lab nunca manda credenciais do navegador.

    
4. Rodar a VM no servidor

    
Fora do navegador não há CORS: os serviços Node do repositório público apk-lab-node-service rodam a mesma VM em Node, e lá as requisições do app saem direto do servidor, com cookies, User-Agent e redirecionamentos como num aparelho. É o caminho para automação ou para apps cujos servidores não podem ser alcançados de uma página.


    
Plugins no player

    
Os plugins do laboratório (docs/PLUGINS.md) também rodam no player, com a mesma API lab: lab.on('screen' | 'log' | 'network'), lab.screen(), lab.composeTree(), lab.viewModels(), lab.layoutBounds(), lab.screenshot() e lab.ui.text/kv/table/json/image/badge/clear. Cada plugin roda no próprio Web Worker, criado numa origem opaca (um iframe em sandbox dentro do frame): o código que sua página envia não ganha a origem do runtime (nem os dados guardados de outros apps). A saída chega à sua página no evento plugin-output, para você mostrar como quiser (use textContent; imagens chegam como Blob).

    
const codigo = `
lab.on('screen', async () => {
  const caixas = (await lab.layoutBounds()).filter(c => c.kind === 'compose' && c.hasImage);
  lab.ui.badge(String(caixas.length));
  lab.ui.table(caixas.slice(0, 20).map(c => ({ nome: c.name, largura: c.size?.width, altura: c.size?.height })), ['nome', 'largura', 'altura'], { id: 'lista' });
  if (caixas[0]) lab.ui.image(await lab.screenshot({ key: caixas[0].key, maxWidth: 360 }), { id: 'primeiro', caption: caixas[0].name });
  lab.ui.image(await lab.screenshot({ maxWidth: 360 }), { id: 'tela', caption: 'Tela inteira' });
});`;

const { plugins, rejected } = await player.plugins.set([{ id: 'componentes', name: 'Componentes da tela', code: codigo }]);
player.plugins.subscribe(plugin => {
  for (const bloco of plugin.blocks) {
    if (bloco.kind === 'image') imagem.src = URL.createObjectURL(bloco.blob);   // revogue a URL anterior
    if (bloco.kind === 'table') console.table(bloco.rows);
  }
});
await player.plugins.stop('componentes');

    
Limites (os mesmos do laboratório): até 32 plugins, 200 mil caracteres de código cada, 16 consultas pendentes, um composeTree por segundo e uma imagem a cada 500 ms por plugin, imagens até 8 MiB, 50 blocos de saída. packageFilter restringe um plugin a pacotes (com.exemplo.*). Plugins que ouvem log ligam a transmissão do Logcat enquanto rodam.


    
Segurança e privacidade

    
    
      
  • O APK fica no navegador. Não há upload: os bytes vão da sua página para o frame e para o Worker. Nada do app é enviado a servidor algum pelo laboratório.
    • 
      
  • Rede só pelo navegador. O app só alcança os hosts permitidos, por fetch (com as regras de CORS do navegador) ou pelo relay opcional que você opera. O laboratório não tem nem hospeda relay.
    • 
      
  • Isolamento. O iframe é sandbox="allow-scripts allow-same-origin" sem permissões (allow=""). Sirva o runtime numa origem diferente da sua página: assim o app não tem acesso a cookies, armazenamento ou DOM dela. Com a mesma origem, o sandbox não isola.
    • 
      
  • Mensagens. Sua página só aceita mensagens do próprio iframe e da origem do runtime; o frame só aceita a janela-mãe, da origem declarada em ?parent=, e responde só para ela. Toda mensagem é versionada e validada (tamanhos limitados, os mesmos validadores da página de testes: sanitizeHostMap, validateMock, permissões, Intent).
    • 
      
  • Plugins em origem opaca. O código de plugin enviado pela sua página roda num Worker de origem opaca, sem acesso ao IndexedDB do runtime.
    • 
      
  • Nada é falsificado. Código nativo protegido não é substituído nem contornado; uma API que a VM não implementa falha com erro explícito (o modo tolerante, que você liga, é sempre relatado no diagnóstico e em diagnostics()). Overrides, mocks e Activities ignoradas são ferramentas de depuração do seu app e aparecem marcadas no diagnóstico.
    • 
      
  • Dados. Só com keep-data os dados do app ficam no IndexedDB da origem do runtime, por pacote e certificado. Estados de permissão do player não são guardados: o evento permission-config entrega o estado para você guardar, se quiser.
    • 
      
  • CSP do runtime. script-src 'self' 'wasm-unsafe-eval', worker-src 'self' blob:, img-src 'self' blob: data:, connect-src 'self' mais os hosts dos APKs e do app, frame-ancestors com os seus sites (e frame-src 'self' about: se usar plugins). Não envie X-Frame-Options: DENY.
    • 
    


    
Limitações

    
    
      
  • Roda o que a VM suporta; o resto termina com um error que diz a fronteira exata (frontier.kind). Bibliotecas nativas, Services em outros processos e muitas integrações do sistema não estão disponíveis.
    • 
      
  • A rede é a do navegador: CORS, cookies e cabeçalhos proibidos, redirecionamentos seguidos pelo navegador, TLS sem acesso aos certificados, sem sockets TCP/TLS crus.
    • 
      
  • Moldura fixa do aparelho (sem skins), presets em dp com densidade 160, sem recorte de câmera.
    • 
      
  • theme muda o modo noturno do app, não a sua página.
    • 
      
  • memoryMiB, tolerateMissing, strictCrash e webview valem no próximo início.
    • 
      
  • Imagens (screenshot) são cortadas dos rasters já desenhados: Views desenhadas pelo DOM da página não aparecem na imagem da tela inteira (o resultado diz quantas em notes).
    • 
      
  • Cada player é um Worker com a própria memória (dezenas a centenas de MB conforme o APK).
    • 
    


    
Protocolo

    
Mensagens { protocol: "apk-player", version: 1, type, … }, validadas dos dois lados (src/player/protocol.js). A versão 1 continua aceita; a revisão 2 é anunciada pelo frame no hello ({ revision: 2, capabilities: [...] }) e acrescenta, sem mudar as mensagens antigas:

    
    
      
  • página → frame: config com id opcional (respondido no config-applied com o mesmo id) e as chaves dos recursos do laboratório; call { id, method, args } com method em openIntent, inspectCompose, layoutBounds, screenshot, screenState, diagnostic, status, answerPermission, subscribe, pluginsSet, pluginsStop, pluginsRestart, pluginsList, stop.
    • 
      
  • frame → página: reply { id, ok, value | error { code, message } }, screen, logcat, network, plugin-output, permission-request, permission-config, stopped.
    • 
    

    
Um frame antigo (revisão 1) responde hello sem capabilities: os métodos novos rejeitam com code: "unsupported" e o resto funciona como antes. A referência em Markdown está em docs/PLAYER.md.
