How an APK runs inside the browser

The lab does not convert or recompile the app. It opens the .apk, reads the Dalvik bytecode inside it and runs it on a virtual machine written in JavaScript, in a Web Worker, on top of an Android framework compiled from the original AOSP sources. This page shows each step and what does not work yet.

Overview

Everything happens on the machine of the person who opens the page. The server only delivers static files; the chosen APK is read by the browser and is not sent anywhere.

  • The app code runs as it is. The Activities, ViewModels, AndroidX, Kotlin and Jetpack Compose packaged in the APK run from its own DEX, instruction by instruction.
  • The Android underneath comes from the original sources. framework.dex is compiled (javac and D8) from sources of AOSP android-13.0.0_r1 and libcore pinned by hash: 6,411 classes in the current build (framework-aosp/manifest.json). Source adaptations are recorded in framework-aosp/ADAPTATIONS.txt.
  • JavaScript only where the device or the browser has to answer. Windows, input, the virtual file system, network, clock, system services and the framework's native functions (JNI) are host contracts written for the lab. Native parts of Android, such as Skia and ICU, come from the original C/C++ source compiled to WebAssembly.
  • The virtual device answers SDK_INT 33. The target is apps with minSdk/targetSdk 24 or higher; behavior that changes with the version follows the app's targetSdk.
  • Nothing fakes success. An API the lab does not implement fails with an explicit error that names it, instead of returning an empty value.

When the bytecode calls a method, the VM decides who runs it, in this order: the APK's bytecode, the AOSP framework bytecode, a framework native with an approved binding, a JavaScript host contract. If none fits, the error points at the missing method.

From APK to screen

Three places work together: the page (the tab you see), the Web Worker where the VM runs and the WebAssembly modules the Worker calls. The page never runs app code; it draws what the Worker sends and returns what you do.

Load and Run do different things

Choosing an APK sends two different messages to the Worker, one after the other. The first, load, prepares everything without running a single line of the app. The second, launch, starts the app's process; it is the same one a tap on the app icon on the device's home screen sends later.

Threads, events and time

A Worker has a single JavaScript thread, but an Android app has dozens. The VM solves this with green threads: each Java thread is an explicit stack of frames, and the scheduler switches threads at safe points (when a thread blocks, ends or spends its instruction quantum). Object.wait, LockSupport.park, Thread.sleep and contended monitors park the thread instead of waiting in JavaScript.

Looper, MessageQueue, Handler, Message and HandlerThread are the original AOSP classes. The lab only implements the native methods of MessageQueue, wired to the scheduler and the virtual clock.

The virtual clock

Every clock the app can read (System.currentTimeMillis, nanoTime, SystemClock, Date, Handler deadlines) reads the same VM clock (src/vm-clock.js). It follows real time and can only move faster, never back. During a Choreographer frame the time stays still at the vsync instant, as on a fast device, so that code measuring “how much of the frame is left” does not see the interpreter's slowness.

Nested runs and deadlocks

Host code that cannot be suspended (a native that called back into Java, a class initializer) waits by letting other threads run on top of the JavaScript stack. If the thread that would wake the wait is stuck underneath that stack, the scheduler reports a deadlock instead of hanging. An exception that escapes from a message run in this nesting is delivered to the message's thread, as on Android, and not to the frame parked underneath it.

Time limits

By default an event can run for up to 25 s and a whole operation for up to 20 s of host time (src/time-limits.js); “Maximum time per event” in Controls raises these limits to 60, 120 or 300 s. No choice removes the limit: an infinite loop ends with the diagnostic report.

Memory

Java objects live in the VM heap as JavaScript records, and arrays in typed storage. A mark-and-sweep collector (src/heap-gc.js) frees whatever became unreachable.

  • Roots: the scheduler threads (frames, registers, pending exceptions), the runtime tables (static fields, Class objects, monitors) and the host state. The sweep of host state is conservative: it may keep garbage alive, but never frees anything reachable.
  • When: at quiet points between events and, under pressure, at the safe points of a long run.
  • References as in ART: WeakReference does not hold the object. SoftReference holds it in a normal collection and is cleared in a collection under pressure, before an OutOfMemoryError. Finalizers do not run.
  • Out of motion: a collection that becomes due while frames are pending or right after an input waits for the first idle moment of the main thread, with a hard ceiling. Measured in docs/INTERACTION-PERFORMANCE.md: in a Compose example the collections during animation dropped from 9 of 9 to 2 of 8.
  • Limit and error: the object limit comes from a memory budget (src/memory-budget.js) that follows navigator.deviceMemory or the “VM memory” choice in Controls. When the heap does not fit even after the emergency collection, the app receives a real OutOfMemoryError, and the report shows who retains the memory.
  • On-demand DEX tables: decoding only what is used reduced the heap of a Compose example from 182 MiB to 68 MiB after loading and from 245 MiB to 158 MiB at the first frame (measured in docs/MEMORY-ON-DEMAND.md).

Rendering

Layout is always computed in the VM, by the original code (onMeasure, onLayout, Compose), never by the page's CSS. The page positions elements in the rectangles the VM computed and shows, inside them, the pixels Skia produced.

  • Views: each View becomes an element positioned in the bounds the VM computed; backgrounds, Drawables, text and shadows are, in general, Skia rasters. Some simple XML widgets are drawn with the page's own elements and therefore have no raster.
  • Compose: the Compose runtime, layout and drawing are the APK's own DEX. The content arrives as a raster, and the page puts on top a transparent layer of controls taken from the Semantics tree, to receive touch, focus and text.
  • Text: text shaping comes from SkParagraph/HarfBuzz; line breaks use ICU's break iterator and Minikin's line-breaking algorithms; font choice walks the Android 13 fallback chain, downloading each Noto font only when a run needs it.
  • Transport: identical rasters travel once and then only as an identifier (content cache in src/raster-cache.js); Canvas and Compose content goes as raw RGBA, without PNG encoding. The Worker does not send a new frame until the page has acknowledged the previous ones (backpressure).

Measured effect in docs/INTERACTION-PERFORMANCE.md: a Compose frame was replayed in about 8.4 ms instead of about 20 ms in the browser Worker, and the displayed rate of the XML example during animation went from 24.3 to 38.9 frames per second, adding up the other changes of that step.

Network

A browser does not open TCP. Everything the app sends to the network goes out through the browser's fetch, under the virtual device's network policy (docs/NETWORK.md).

  • TLS belongs to the browser. An app's SSLSocket does not encrypt anything in the VM: it presents a certificate chain the lab generated for the session (like a debugging proxy), and the browser validates the real certificate. An app that pins the real server's key refuses that chain, and the refusal is the app's own.
  • Only HTTP/1.x over a socket. A conversation that is not HTTP/1.x fails on the first bytes with an error that names them. Loopback (the app's own ServerSocket on 127.0.0.1) works.
  • CORS. The servers of a real app rarely authorize the lab's origin: see CORS and how to solve it.

CORS and how to solve it

On a phone, the app talks straight to the server. Here, the request is made by the browser's fetch, from the origin of the lab page. The browser only hands the response to the page if the server authorizes that origin (CORS, Cross-Origin Resource Sharing). A real app's API was built for the app, not for a web page, and almost never authorizes it: the request goes out, the server answers, and the browser discards the response.

How it shows up

  • In the app: the call fails like a connection failure (Java receives an IOException), not like an HTTP response.
  • In the Network panel: the entry is shown as a failure, with the explanation that the destination did not answer CORS for the page. The browser console (F12) shows the block by name.
  • Preflight: requests with custom headers (Authorization, Content-Type: application/json…) or methods such as PUT/DELETE first send an OPTIONS; if the server does not answer it, the real request is never sent.
  • Local server from the public site: an https page calling http://localhost also goes through Chrome's private network check (Private Network Access), which asks for an extra preflight.

Four ways to solve it

  1. Local CORS relay (to use the real API). A small Node program that runs on your machine, repeats each request as the phone would and returns the response to the page with the CORS headers. It listens only on 127.0.0.1, requires the token printed at startup, accepts only the lab's origin (the public site and a local copy, by default), answers the private network preflight, follows redirects and returns the Set-Cookie headers, which the browser would hide. It reaches any destination, including servers on this machine or the local network (localhost, 192.168…). It stores nothing. 
    # Node 18 or newer
curl -O https://madmax-dev-br.github.io/apk-browser-lab-site/tools/cors-relay.mjs
node cors-relay.mjs
# options: --port 8787 · --origin <page origin> (repeatable) · --token <token>
    You can also download the file directly: cors-relay.mjs. Copy the Proxy URL it prints into Controls › Device › Proxy (in the embedded component, the proxyUrl option). The {url} in the URL is replaced with each request's destination.
  2. Endpoint mock (no network). In Controls › Endpoint mocks, the response comes from the lab itself and the request never goes out, so there is no CORS. Good for screens that depend on a specific response.
  3. Redirect to a server of your own. In Controls › Redirect hosts, send the API host to a server you control (a mock server, a debugging proxy, a test environment). That server must answer CORS for the lab's origin, including on OPTIONS: 
    Access-Control-Allow-Origin: https://madmax-dev-br.github.io
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Expose-Headers: Location, ETag   # the response headers the app needs to read
Access-Control-Allow-Private-Network: true      # only when the server is local and the page is https
Vary: Origin
    The VM never sends the browser's cookies (the app's cookies go as its own headers), so Allow-Credentials is not needed; the app only sees the response headers listed in Expose-Headers. A local server without CORS also works by combining the redirect with the relay.
  4. Run the VM on the server. The Node services in the public apk-lab-node-service repository run the same VM outside the browser: there is no CORS there, and requests go out directly (respecting the session's host list, redirects and mocks).

The allowed hosts list, the mocks and the redirects keep applying with any of these ways: the only thing that changes is who makes the exchange with the server.

Native code

ARM or x86 .so libraries do not run in the browser. The lab takes another path:

  • Android native code, from the original source. Skia (CanvasKit), ICU, resource selection (ResTable_config::match), AOSP's Path curve approximation, BoringSSL and the Conscrypt JNI layer are compiled from C/C++ to WebAssembly, with hashes and provenance.
  • Open-source libraries in wasm32. For open libraries that apps load (for example Hermes, React Native, fbjni, SQLCipher), the lab has wasm32 builds with provenance.json and a pinned SHA-256. Its own dynamic linker (src/native-linker.js) links them into a per-process memory, and the bytes are only fetched when the app calls System.loadLibrary.
  • JNI. The JNI bridge (src/jni-host.js) gives those libraries the JNI function table; a function not yet implemented fails with a specific error.
  • No build, no execution. An app library without a matching build produces an explicit UnsatisfiedLinkError; the app only continues if it handles the error itself.
  • Protection is never bypassed. Libraries that look like app protection, anti-fraud or attestation (src/protected-native.js) never get a stub, not even in tolerant mode. Integrity checks, root or emulator detection and the app's encryption run as the app wrote them, or fail.

Static work queue of the framework natives: docs/NATIVE-CLOSURE.md.

Tools

The Controls panel and the panels below the device are for testing and understanding the app. Every tool that changes the app's behavior is counted, announced in Logcat and listed in the Summary.

  • OpenDeep links and Intents resolved by the manifest's intent filters, like am start.
  • AppearanceDark theme, font scale, language and region, orientation, screen, gesture or button navigation, animation scale, layout bounds.
  • Device24-hour clock, time zone, battery, connectivity, allowed hosts and proxy.
  • PermissionsDangerous permissions from the manifest (ask, grant, deny) and simulated location.
  • ExecutionVM memory, maximum time per event, tolerant mode, strict failure mode, app data.
  • Method returnsMakes a chosen method return a value without running its body.
  • Ignored activitiesDrops the app's requests to open certain Activities.
  • Redirect hostsSends the requests of one host to another destination, like /etc/hosts.
  • Endpoint mocksAnswers requests that match a pattern, without going to the network; exports and imports JSON.
  • PluginsJavaScript snippets of your own that watch the app, crop the screen, reload the screen, create mocks and open windows with their own layouts. How to set up.
  • Logcat and NetworkThe android.util.Log lines and every request, refusal and mock. Right-click a request: create a mock of it (already filled with method, URL, status, headers and the response body) or redirect the host.
  • ComposeThe screen elements cropped from the frame by the layout bounds, with details and the full tree.
  • Summary and diagnosticsMemory, who retains it, exceptions, main thread and busiest methods; “Copy diagnostics” takes the whole report.
  • PlayerThe <apk-player> element to embed an APK in another page (docs/EMBED.md).

Validation against Android

Five examples (stateful Compose, Compose with navigation, hybrid navigation, an approvals flow in Compose and a projects app in XML) are validated by scripts/check-validation.mjs. Each must pass everything: the complete flows in the VM, zero unresolved APIs and zero errors, page captures compared with Android's (parity), layout check, the same flows in the browser with real touches and the collector in audit mode. The evidence is pinned to the framework SHA and goes stale with every rebuild.

Limitations

The lab is experimental. These limits are in the code and in the project's documentation:

  • Not every Android API exists.In the APKs of the public catalog, 886 of 7,865 referenced platform methods (11.3%) still have no implementation, concentrated in graphics, Views and widgets (docs/CORE-GAPS.md). Calling one is an explicit error with the method name.
  • It is a JavaScript interpreter.There is a baseline compiler, but not an optimizing JIT. A Compose frame still runs about 350,000 instructions at about 100 ns each, which alone limits a Compose animation to around 28 frames per second (docs/INTERACTION-PERFORMANCE.md).
  • CPU drawing.Skia rasterizes on the CPU in the Worker; there is no RenderThread and no GPU. 3D rotation of Views fails explicitly.
  • Network only through the browser.No TCP, no real UDP, no inbound connections. What the server does not authorize through CORS does not get through without the relay; browser blocking extensions also stop requests.
  • WebView loads in the browser itself.The content of a WebView is an iframe of the page, subject to the browser's rules; WebView pages do not go through endpoint mocks.
  • Native code only with a wasm32 build..so libraries without a matching build do not run and produce UnsatisfiedLinkError.
  • Protection is not faked.Integrity checks, attestation, root or emulator checks and protected natives run as they are or fail; the lab does not change device identifiers to get past them.
  • Services the virtual device does not have.Google Play services do not exist here; its location client, for example, fails explicitly.
  • Floating action bar only.View.startActionMode with ActionMode.TYPE_FLOATING follows AOSP (the floating copy-and-paste bar appears over the screen and the click reaches onActionItemClicked). The primary mode (TYPE_PRIMARY, the contextual bar at the top of the window) only works when the app provides its own bar, such as AppCompat; without it, it fails explicitly.
  • Menus need a bar of the app.Menu XML (MenuInflater), submenus, menu shortcuts, android.widget.Toolbar with its overflow and PopupMenu are the original Android classes. The lab's windows have no action bar of their own: the options menu appears when the app puts it in a Toolbar (setActionBar) or uses AppCompat's bar. On a window without a bar the menu is still created for keyboard shortcuts, and openOptionsMenu fails explicitly.
  • Software keystore.The Android Keystore is a software KeyMint: isInsideSecureHardware() is false, and there is no StrongBox and no attestation key.
  • Text is not identical to the device's.Text shaping comes from SkParagraph, not the whole of Minikin; there are no hyphenation patterns. Breaks and metrics may differ in rare cases.
  • Browser memory.The browser uses much more than the Java heap: DEX tables, the CanvasKit heap, rasters. A very large tab may be terminated by the browser.
